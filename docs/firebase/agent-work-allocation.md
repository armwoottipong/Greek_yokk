# แนวทางแบ่งงานให้เอเจนต์

ก่อนมอบหมายแต่ละครั้ง ให้โมเดลหลักประเมินขอบเขต ความกำกวม ความเสี่ยงต่อข้อมูลสูญหาย การทำงานพร้อมกัน และความปลอดภัยก่อน งานในเอกสารนี้เป็นต้นแบบ Emulator เท่านั้น แอปขายยังไม่ได้เชื่อม Firebase ไฟล์กฎสำหรับ deploy ยังปฏิเสธการอ่านเขียน และยังไม่ได้ deploy จริง ต้องรักษาข้อกำหนดเดิม: ทุกบัญชี Google มีสิทธิ์เท่ากัน, เขียนข้อมูลร้านไม่ได้เมื่อออฟไลน์ และห้ามเข้าคิวหรือยืนยันการขายก่อนเซิร์ฟเวอร์รับรอง

## เกณฑ์หลัก: ประหยัด token รวม โดยรักษาคุณภาพ

ตามคำสั่งผู้ใช้ล่าสุด เลือกโมเดลและระดับ reasoning ต่ำสุดที่ทำงานผ่านเกณฑ์ได้ ไม่ให้ความเร็วเป็นเป้าหมายหลัก
ประเมินต้นทุนทั้งงาน: บริบทที่ส่ง การตอบ การตรวจทาน และการแก้งาน ไม่ถือว่าใช้โมเดลเล็กแล้วประหยัดเสมอ
หากงานสั้นกว่าบริบทที่ต้องส่งและค่าตรวจทาน ให้โมเดลปัจจุบันทำเอง ไม่สร้างเอเจนต์เพียงเพื่อใช้โมเดลต่ำลง

ก่อนเริ่มแต่ละส่วน บันทึกสั้น ๆ ใน ledger: ขอบเขต/ความเสี่ยง ผู้รับผิดชอบและโมเดล เหตุผล เกณฑ์ตรวจผ่าน
ใช้ไฟล์และผลตรวจที่มีอยู่ ไม่ให้เอเจนต์อ่านประวัติทั้งแชตซ้ำ ไม่ทำหลายตัวเพื่อแข่งความเร็ว
ไม่อ้างจำนวน token หรือเปอร์เซ็นต์ที่ประหยัดได้หากไม่มีข้อมูลวัดจริง

## เลือกผู้ทำงาน

- ใช้ `gpt-6-luna` ระดับ low กับเอกสารที่ทราบขอบเขต, ข้อความ UI ภาษาไทย, สรุปสถานะ และการสำรวจแบบอ่านอย่างเดียว
- ใช้ `gpt-6-luna` ระดับ medium ได้กับ helper หรือ component ขนาดเล็กที่แยกชัด หลังโมเดลหลักกำหนดสัญญาและตัวอย่างผลลัพธ์แล้ว
- งานหลายไฟล์ที่แบบชัดและความเสี่ยงปานกลาง ใช้โมเดลระดับกลางที่เครื่องรองรับเมื่อประเมินว่าคุ้มกว่าการให้โมเดลหลักทำและตรวจเอง เริ่ม reasoning ต่ำแล้วเพิ่มเฉพาะเมื่อมีเหตุผล
- ให้โมเดลหลักรับผิดชอบ Firebase Rules, การจัดสต็อกเมื่อหลายเครื่องเขียนพร้อมกัน, การยกเลิกบิล, codec และ migration ขั้นสุดท้าย ตลอดจนสถาปัตยกรรมข้ามโมดูล ไม่เปิดเอเจนต์โมเดลใหญ่ซ้ำโดยไม่มีงานตรวจอิสระที่จำเป็น
- เริ่มด้วยเอเจนต์โมเดลต่ำไม่เกินหนึ่งตัว เว้นแต่มีงานอิสระหลายชิ้นจริง ระบุเจ้าของไฟล์เพียงคนเดียวต่อไฟล์ และส่ง prompt สั้นที่ระบุเป้าหมาย ขอบเขต ไฟล์ และเกณฑ์เสร็จ แทนการส่งประวัติทั้งหมด
- โมเดลหลักตรวจ diff หรือผลลัพธ์และการตรวจที่เกี่ยวข้องก่อนรวม หากผิดสัญญาสำคัญ ให้แก้คำชี้แจงหนึ่งรอบ; ถ้ายังผิดซ้ำหรือพบ dependency/ความเสี่ยงที่ไม่ได้กำหนด ให้ยกระดับกลับมาวิเคราะห์ ห้ามลองวนโดยไม่มีหลักฐานใหม่ ห้ามลดความเข้มของการทดสอบเพื่อให้ผ่าน และห้ามรัน Emulator suite พร้อมกัน
- รันเฉพาะการตรวจที่ครอบคลุมผลกระทบก่อน ขยายชุดเมื่อพบเหตุผล ไม่รันทดสอบซ้ำหรืออ่านไฟล์ใหญ่ซ้ำหลังผ่านแล้วโดยไม่มีการเปลี่ยนแปลง

แนวคิดเลือกตามเกณฑ์คุณภาพและทดสอบก่อนลดขนาดโมเดลอ้างอิง [OpenAI Docs: Model selection](https://developers.openai.com/api/docs/guides/model-selection)
ชื่อโมเดลที่เรียกจริงต้องใช้รายการที่เครื่องรองรับในขณะนั้น เอกสารนี้ไม่เปลี่ยนโมเดลหลักหรือการตั้งค่าบัญชีโดยอัตโนมัติ

## จัดกลุ่มงานคงเหลือ

**เหมาะกับเอเจนต์หลังมีสัญญาชัดเจน:** เอกสารและข้อความภาษาไทย, สำรวจโค้ด/รูปแบบข้อมูลแบบอ่านอย่างเดียว, helper ที่แยกจากกฎธุรกิจ, UI component เล็กที่รับ input/output กำหนดไว้แล้ว งานเหล่านี้ช่วยเตรียมส่วนย่อย แต่ยังไม่รับรองการทำงานจริง

**ต้องให้โมเดลหลักกำหนดแบบก่อน:** ขยายโปรไฟล์วัตถุดิบเกิน 15 รายการ, แก้หน่วย/ชนิด/สูตรผลิต, คำสั่งโครงสร้างหมวดและช่องทาง, ร่างสต็อกหลายชนิด, ข้อจำกัดตัวเลข/ขนาดเอกสาร/ประวัติ/คำขอ และ invariants ของ import เป็นงานที่เชื่อมกัน ต้องออกแบบข้อมูลและกฎก่อนจึงค่อยแยก helper ได้

**งานหลักที่ไม่ควรมอบหมายการตัดสินใจ:** เลือกและพิสูจน์นโยบาย production, protocol/codec สาธารณะ, adapter เตรียมราคาและ commit ออนไลน์, การกระทบยอด journal, login/store/listeners/reports, migration/restore และ E2E สองเบราว์เซอร์ ต้องรักษาการ commit ขายและสต็อกแบบอะตอม และตรวจการเชื่อมโยงทั้งระบบ งานเหล่านี้ยังไม่พร้อมทำคู่ขนานทั้งหมด

ข้อกำหนดและสถานะอ้างอิงจาก `production-readiness.md` และ `prepared-model-experiment.md`; ผล Emulator ปัจจุบันเป็นหลักฐานของต้นแบบเท่านั้น ไม่ใช่หลักฐานพร้อมใช้งานจริง
