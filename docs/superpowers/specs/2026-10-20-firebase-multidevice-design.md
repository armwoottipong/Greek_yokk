# ย้าย Greek Yogg ไป Firebase Spark สำหรับหลายเครื่อง

สถานะ: ผู้ใช้ปรับขอบเขตวันที่ 20 ตุลาคม 2026 — ล็อกอิน Google อย่างเดียว ทุกบัญชีใช้งานเท่ากัน ไม่ใช้ role หรือระบบอนุมัติสมาชิก; ยังไม่ได้ย้ายข้อมูลจริง

## ข้อกำหนดที่ผู้ใช้ยืนยัน

- หลายเครื่องใช้ยอดขายและสต็อกชุดเดียวกัน
- อินเทอร์เน็ตหลุดให้หยุดยืนยันการขายชั่วคราว
- ใช้แพ็กเกจฟรี ไม่เปิด Blaze หรือผูก billing เพื่อการย้ายครั้งนี้

## แนวทางที่เสนอ

ใช้ Firebase Spark: Authentication ผ่าน Google + Cloud Firestore Standard edition
เว็บ Vue/Pinia เชื่อม Firestore โดยตรง ใช้ transactions สำหรับข้อมูลที่ต้องบันทึกพร้อมกัน
Security Rules เป็นผู้บังคับสิทธิ์และข้อกำหนดข้อมูลบน Firebase ไม่อาศัย validation หน้าเว็บอย่างเดียว
ไม่ใช้ Cloud Functions, Cloud Storage, scheduled jobs หรือ managed backup ที่ต้องเปิด billing
เว็บยังใช้ GitHub Pages ตามเดิมได้

ตัวเลือกเดิมแบบ Cloud Functions ถูกตัดออกเพราะผู้ใช้เลือกใช้ฟรี
ไม่ใช้ snapshot ทั้งร้านเป็นเอกสารเดียว เพราะชนกันง่ายและติดขนาดเอกสาร

## ขอบเขตเริ่มต้นและสมมติฐาน

ร้านเดียวหลายเครื่อง บัญชี Google ที่ล็อกอินสำเร็จทุกบัญชีใช้งานได้เท่ากัน
ไม่ใช้ role เจ้าของ/พนักงาน ไม่ต้องอนุมัติสมาชิกหรือเก็บ UID เจ้าของคนแรก
ทุกบัญชีที่ล็อกอินขาย จัดการคลัง สูตร ราคา และยกเลิกบิลได้ ผ่านคำสั่งที่ตรวจข้อมูลและบันทึกพร้อมกัน
ข้อกำหนดนี้แทนที่แบบสิทธิ์สมาชิกเดิม ตามคำสั่งผู้ใช้วันที่ 20 ตุลาคม 2026
ตะกร้าและแบบร่างเป็นของแต่ละเครื่อง ส่วนข้อมูลร้านเป็นข้อมูลร่วม
ไม่รวมหลายสาขา ขายออฟไลน์ และการรับชำระเงินผ่านผู้ให้บริการภายนอก

## โครงสร้างและการบังคับกติกา

- จัดข้อมูลใต้ shops/{shopId} แยกเมนู สูตร ของเสริม ช่องทาง วัตถุดิบ ล็อต บิล การเคลื่อนไหว และคำสั่งกันซ้ำ
- ใช้เอกสารย่อยสำหรับรายการที่ต้องตรวจแยก แทน arrays ขนาดไม่จำกัดที่ Rules ตรวจทุกสมาชิกไม่ได้
- การเคลื่อนไหวแต่ละรายการระบุ material, lot, order/operation, จำนวน และ revision ก่อน/หลัง
- Rules ตรวจการล็อกอิน schema ฟิลด์ที่แก้ได้ revision ยอดไม่ติดลบ และความสัมพันธ์ระหว่างการเคลื่อนไหวกับยอดที่เปลี่ยนผ่าน getAfter()
- ห้ามแก้ประวัติขายที่จบแล้วโดยตรง การยกเลิกเป็นธุรกรรมแยกและทำได้ครั้งเดียว
- ค่าเงินและจำนวนใช้หน่วยย่อยจำนวนเต็มที่กำหนดร่วมกันระหว่างเว็บกับ Rules พร้อมตรวจความละเอียดของข้อมูลเดิมก่อนแปลง
- คำนวณใน shared domain functions บนเว็บ แต่ข้อกำหนดที่ป้องกันการปลอมราคา สูตร หรือยอดตัดต้องบังคับซ้ำใน Rules
- ต้องออกแบบและพิสูจน์ Rules ด้วย Emulator ก่อนสรุปแบบรายละเอียดและเริ่มย้ายข้อมูล ไม่รับรองว่ากติกาที่ซับซ้อนเดิมทั้งหมดตรวจได้โดยไม่จำกัดขนาดบิล
- กำหนดขอบเขตจำนวนรายการ/ล็อตที่ transaction รองรับจากงบ Rules จริง: 10 document access calls ต่อ operation และ 20 ต่อ transaction รวมทั้งเพดาน expressions ไม่เดาตัวเลขบิลล่วงหน้า
- หากตรวจครบไม่ได้ ให้หยุดก่อน production และเสนอปรับโมเดลหรือขอบเขตที่ตรวจได้ ห้ามลดเหลือเพียงตรวจว่าล็อกอินแล้ว
- ทุกธุรกรรมที่ต้องสำเร็จพร้อมกันต้องไม่แยกเป็นหลาย commit เพื่อหลบข้อจำกัด

## การขายและเครือข่าย

1. สร้าง operation ID ถาวรและเก็บ payload บนอุปกรณ์ก่อนส่ง
2. transaction อ่านคำสั่งเดิม ราคา สูตร สต็อก และล็อตล่าสุดก่อนเขียน
3. คำนวณบิลและการตัดสต็อกจากข้อมูลล่าสุด หากราคา สูตร หรือยอดขาดเปลี่ยน ให้ผู้ใช้ตรวจยืนยันใหม่
4. บันทึกบิล การเคลื่อนไหว สต็อก ยอดขาด และผลคำสั่งพร้อมกัน โดย Rules ตรวจความสัมพันธ์
5. ส่งซ้ำ ID เดิมและ payload เดิมคืนบิลเดิม ID เดิมแต่ payload ต่างกันต้องปฏิเสธ
6. ล้างตะกร้าและเปิดใบเสร็จเมื่อได้ผล commit ที่ยืนยันแล้วเท่านั้น ใช้ server timestamp และวันธุรกิจ Asia/Bangkok

ออฟไลน์ดูข้อมูลที่เคยโหลดและแก้ตะกร้าได้ แต่หยุดบันทึกข้อมูลร้านทุกประเภท
ไม่ใช้ navigator.onLine เป็นหลักฐานว่าส่งสำเร็จ และไม่เปลี่ยนเป็น queued offline writes
หากส่งแล้วคำตอบหาย ให้คงสถานะรอตรวจสอบผลและ operation ID เดิม แม้ reload
เมื่อเชื่อมต่อใหม่อ่านสถานะจากเซิร์ฟเวอร์ หากยังไม่พบจึง retry ด้วย ID เดิมได้
ไม่สร้างการขายใหม่เพื่อแทนรายการที่ยังไม่ทราบผล
คงขั้นตอนยืนยันยอดขาดเดิม แต่ความยินยอมต้องตรงกับรายการและยอดขาดล่าสุด

## คลังและการอ่านร่วมกัน

รับเข้า ผลิต ทิ้ง เปลี่ยนล็อต ตรวจนับ ยกเลิกบิล และยืนยันแบบร่าง ใช้ transaction และ ID กันซ้ำ
แบบร่างอ้าง revision หากชนการแก้อีกเครื่องต้องแจ้งขัดแย้ง ไม่ทับยอดเก่าทั้งร้าน
ใช้ listeners เฉพาะข้อมูลที่ใช้งาน ประวัติขายแบ่งช่วงวันและแบ่งหน้า
ยกเลิก listeners เมื่อออกจากระบบและล้างข้อมูลในหน่วยความจำ
ไม่เปิด persistent cache ที่ทำให้ผู้ใช้บัญชีถัดไปเข้าถึงข้อมูลบัญชีเดิม
localStorage เก็บตะกร้า แบบร่าง และสถานะรอผล ไม่ใช่ฐานหลักและไม่ upload snapshot ทับข้อมูลกลาง

## ย้ายข้อมูล

เลือกเครื่องต้นทางที่ข้อมูลครบที่สุดและ export JSON เก็บก่อนย้าย
ตรวจ schema ปัจจุบันจากโค้ด (ปัจจุบัน 4) IDs สูตร references ล็อต และยอดรวม
นำเข้าด้วยเครื่องมือ local ของผู้ดูแลที่ยืนยันสิทธิ์บนเครื่อง ไม่ใส่ admin key ในเว็บหรือ git
Firebase CLI ใช้ deploy Rules/indexes ส่วนเครื่องมือนำเข้าที่ใช้ Admin SDK ต้องตั้ง Application Default Credentials แยกกัน การ login CLI ไม่ได้ให้ ADC โดยอัตโนมัติ
นำเข้าแบบส่งซ้ำได้ภายใต้สถานะ importing ที่ client ปกติเข้าถึงไม่ได้ ตรวจความครบก่อน activate
หยุดบันทึกระบบเดิมก่อนนำเข้าชุดสุดท้าย แล้วเปิดทุกเครื่องใช้ฐานใหม่พร้อมกัน
เก็บข้อมูลเดิมไว้เพื่อกู้คืน แต่ไม่เปิดรับขายระบบเก่าและใหม่คู่ขนาน
สำรองด้วย JSON จากข้อมูลกลาง การ restore ต้องเป็นงานผู้ดูแลโปรเจกต์ระหว่างหยุดธุรกรรม
หากย้อนกลับต้อง export ฐานกลางล่าสุดก่อน ไม่ใช้ snapshot เก่ารับขายทันที

## โควตาและข้อจำกัดใช้ฟรี

Firestore ฟรีปัจจุบัน: เก็บ 1 GiB อ่าน 50,000 documents/วัน เขียน 20,000/วัน ลบ 20,000/วัน และส่งออกเครือข่าย 10 GiB/เดือน
จำนวน reads/writes คิดตามเอกสาร ไม่ใช่จำนวนบิล ต้องนับ listeners, Rules reads และ retries ด้วย
โควตารายวันรีเซ็ตราวเที่ยงคืน Pacific ไม่ใช่เวลาไทย
Spark ไม่เรียกเก็บส่วนเกินอัตโนมัติ แต่เมื่อเกินโควตาอาจใช้งานส่วนนั้นต่อไม่ได้จนโควตารีเซ็ต จึงกระทบการขายได้
ห้ามอ้างว่าพอสำหรับร้านจนกว่าจะทราบจำนวนเครื่อง บิล และจำนวนเอกสารเฉลี่ยต่อธุรกรรม
เมื่อพบ quota error ต้องเก็บตะกร้าและแจ้งผู้ใช้ ไม่แสดงว่าขายสำเร็จ
ไม่มี managed automatic backup/PITR ในขอบเขตนี้ ใช้ JSON export ที่ผู้ใช้จัดเก็บเอง

## การตรวจรับก่อนเปิดใช้

- Rules ปฏิเสธผู้ไม่ล็อกอิน การปลอมยอดนอกคำสั่งที่ถูกต้อง และการตัดล็อตผิด; ผู้ล็อกอินทุกคนใช้งานได้เท่ากันโดยไม่ต้องตั้ง role
- สองเครื่องขายพร้อมกันไม่มี lost update การยอมรับยอดขาดตรงกับข้อมูลล่าสุด
- กดซ้ำ timeout retry และ reload ไม่สร้างบิลหรือตัดล็อตซ้ำ
- ออฟไลน์ก่อนขายไม่บันทึก ไม่ออกใบเสร็จ และไม่เข้าคิวขายอัตโนมัติ
- ขายสำเร็จแต่คำตอบหายกู้บิลเดิมได้
- ปรับคลังพร้อมขาย แบบร่างเก่า และยกเลิกพร้อมกันไม่เขียนทับหรือคืนยอดซ้ำ
- ทดสอบรายการสูงสุดที่อนุญาตด้วย Rules จริง และปฏิเสธรายการเกินก่อนบันทึก
- import ซ้ำ ขาดช่วง และ export round-trip ไม่สูญข้อมูล
- รัน npm test, npm run lint, npm run build และ Emulator integration tests พร้อมทดสอบเว็บสอง session

## ข้อมูลที่ต้องใช้ก่อนเชื่อมระบบจริง

โปรเจกต์ที่ผู้ใช้ระบุคือ `yoggie-db` และได้ส่ง Firebase web config มาแล้ว
ผู้ใช้แจ้งว่าตั้งค่า Firestore, Google Sign-in และ authorized domain ครบแล้ว แต่ยังไม่ได้ตรวจผ่าน API หรือทดสอบเชื่อมต่อจริง
ที่ตั้งจริงของฐานข้อมูลยังไม่ได้ตรวจยืนยันจากระบบ ไม่อนุมานจาก region ที่เคยแนะนำ
ยังต้องใช้เครื่องต้นทางข้อมูลจริงและปริมาณใช้งานโดยประมาณก่อนเปิดใช้จริง; ไม่ต้องใช้ UID เจ้าของหรือ bootstrap สมาชิก
เอกสารนี้ไม่เปิด billing ไม่สร้าง project และไม่ย้ายข้อมูลจริง
